# Feature decisions: 8 October 2026

These notes combine the original shipment, fulfillment/return, and
catalog/storefront/observability designs and implementation plans.
Use the [current guides](../README.md) for commands and API behavior.

## Event-driven shipments

Payment success saves an `OrderPaid` event in the SQL Outbox. The existing
RabbitMQ consumer creates a Pending shipment after delivery. This uses the same
publisher and retry flow as catalog events.

The handler validates the order/payment against SQL, locks the order row, and
commits the shipment and processed-message marker together. A unique order ID
prevents two shipments. Same-ID redelivery is ignored; another valid event ID
retains the existing shipment. A failed marker write rolls back shipment creation.

This approach was chosen over creating shipments inside PaymentService or adding
a separate shipping service. It demonstrates asynchronous delivery while keeping
one application. Already-processed historical paid events are not backfilled.

The first shipment design only created Pending records. Later work added status
updates, tracking, and history; see fulfillment (removed feature).

## Fulfillment and returns

The next design added admin shipment lists, atomic status history, owner tracking,
and whole-order returns. Separate shipment and return permissions control operators.
Customer timelines omit operator identity; admin history includes trusted actors.

ReturnService uses the order/payment/return lock order and delegates refunds to the
existing RefundService. A return completes only after full successful refund
settlement. Returns do not automatically restock inventory or change order status.
Concurrent updates, refund/completion races, duplicate requests, and forced storage
failures were included in the verification plan.

The original execution note records six implementation tasks, batched HTTP checks,
and two review findings fixed with SQL/HTTP regression checks. Full original notes
are retained in the local documentation backup; this summary does not rerun those checks.

## Catalog, storefront, and telemetry

The design added SQL product browsing/details, sorted Elasticsearch search,
version-checked product editing, and a simple React + TypeScript storefront.
Catalog edits preserve reserved stock and save search events in the same SQL transaction.

The UI uses hash routes and memory-only bearer sessions. It keeps uncertain
checkout/payment idempotency keys so a retry can recover the saved operation.
Product deletion and stock editing were outside the agreed scope.

OpenTelemetry records business metrics and dependency traces. Outbox rows retain
trace context for delayed RabbitMQ publication; this does not store complete
telemetry history in SQL. The optional local dashboard receives exported data and
is independent of API readiness.

The implementation plan grouped work into catalog APIs, instrumentation, and the
storefront. Its review focus covered private UI state, uncertain writes, concurrent
catalog/stock updates, safe telemetry attributes, and durable trace context.
