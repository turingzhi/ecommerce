# RabbitMQ event delivery

Create `.env` from `.env.example` and set a strong SQL Server password before any Compose command, then start the broker with `docker compose up -d rabbitmq`. For the local verification, run `dotnet run -- --verify-rabbitmq`. If the full Compose stack is running, first use `docker compose stop ecommerce` so the API does not compete for verification messages on the same queue; resume it with `docker compose up -d --wait ecommerce`. The verification uses a temporary SQLite database and the real local RabbitMQ container; it does not use the API's SQL Server database. To run the API itself, configure `ConnectionStrings:ShopDatabase` for SQL Server. When running the API outside Docker, the RabbitMQ defaults are `localhost:5672`, user `guest`, password `guest`; override them through the `RabbitMq` configuration section if needed.

The Outbox worker reads unpublished SQL records. `RabbitMqEventPublisher` declares a durable direct exchange and durable queues, publishes a persistent JSON event with the stable Outbox ID, and waits for a publisher confirmation. It uses mandatory routing so an unbound routing key fails. Only then does the dispatcher set `PublishedAt`. If the broker connection fails, the record stays pending with backoff; transport failures do not permanently dead-letter it. An unroutable or rejected publication follows the existing five-attempt Outbox dead-letter policy.

`RabbitMqConsumerWorker` takes one delivery at a time and calls `EventConsumer`. That consumer inserts the event ID into `ProcessedMessages` in its database unit of work. The RabbitMQ acknowledgement follows the successful database save. If the acknowledgement is lost, RabbitMQ can redeliver; the saved ID makes that repeat harmless. This is at-least-once delivery, not exactly-once delivery.

On a processing failure, the worker first publishes the original body to a durable retry queue with a confirmed publish, then acknowledges the original. The retry queue has a two-second TTL and returns expired messages to the main exchange. Non-transient failures reach a dead-letter queue after five attempts. Database failures and temporary Elasticsearch outages keep events retryable until recovery. If moving a message fails, the worker requeues the original instead. For product events, the consumer indexes Elasticsearch before saving the processed ID.

The broker integration verification checks a confirmed Outbox publication, duplicate delivery, unroutable routing, an unreachable broker and later recovery, a temporary consumer database failure even when its delivery is already at attempt four, and a poison event reaching the dead-letter queue after five attempts.
